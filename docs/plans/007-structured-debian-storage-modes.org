* Structured Debian Storage Modes

** Goal

Implement structured =storage.mode= support in Shoelaces Debian preseed
rendering so Debian installs can render a plain GPT/UEFI partition layout, the
existing LVM layout, or a two-disk mdadm RAID1 layout from the same structured
provisioning model.

At minimum, Debian preseed rendering must support:

- =regular=
- =lvm=
- =raid=, initially focused on two-disk RAID1 for servers with mirrored M.2
  install disks

Unknown storage modes must fail rendering or validation with a clear error
instead of silently falling back to another layout.

** Context

Shoelaces mappings now expose structured storage config, including:

- =provisioning.Storage.Mode=, with expected values such as =regular= or =lvm=
- =provisioning.Storage.Disk=, for example =/dev/nvme0n1=
- =provisioning.Storage.VolumeGroup=, for example =vg0=
- =provisioning.Storage.Wipe=
- =provisioning.Storage.WipeDiskPatterns=
- =provisioning.Storage.Filesystems=, currently root and swap entries

RAID needs additional structured data because =storage.disk= names one primary
install disk and =wipeDiskPatterns= is intentionally destructive selector data,
not layout data. A RAID1 install needs explicit member disks, for example:

#+begin_src yaml
storage:
  mode: raid
  raid:
    level: 1
    devices:
      - /dev/nvme0n1
      - /dev/nvme1n1
    bootDegraded: true
#+end_src

Today the embedded Debian preseed template accepts =storage_mode= but still
renders an LVM-oriented recipe regardless of mode. A render-validation test also
sets =Mode: "regular"= while asserting an LVM =vg_name= stanza, so the tests do
not currently describe the desired behavior.

** Boundaries

- This plan implements Debian preseed storage rendering only.
- Preserve the public template name =preseed/debian= and existing config URLs.
- Preserve =boot_ref= and =ref= query behavior for server-side boot session
  rendering.
- Do not redesign the full structured storage schema beyond the narrow RAID
  fields needed for Debian RAID1. Use existing fields where possible.
- Keep the existing =preseed/storage= template URL available. The new Debian
  RAID support may reuse its partman-md approach, but should not break callers
  that still render =preseed/storage= directly.
- Do not change CentOS kickstart, CoreOS/cloud-init, or Ubuntu minimal storage
  rendering in this plan unless a regression test proves an existing path was
  accidentally affected.
- Keep existing Debian 12 and Debian 13 target rendering working.
- Support Debian RAID mode for UEFI boot only in this plan. BIOS RAID boot
  should fail validation/rendering clearly until intentionally designed.
- Intentionally change the built-in Debian/default storage mode from =lvm= to
  =regular= going forward.
- Keep existing =mappings.yaml= examples valid, and update examples/docs so any
  LVM installs opt in explicitly with =storage.mode: lvm=.

** Current State

- =mappings.ParamsWithProvisioning= projects =Storage.Mode= to
  =storage_mode= and =Storage.VolumeGroup= to =vg_name=.
- Structured storage does not currently have RAID member-disk fields.
- Built-in provisioning defaults still set =storage_mode= to =lvm=.
- Mapping validation currently accepts =plain=, =lvm=, =raid=, and =manual=.
- The embedded Debian preseed template always renders LVM module loading,
  LVM cleanup prompts, a PV, and root/swap LVs.
- A separate =preseed/storage= template already demonstrates
  =partman-auto/method string raid=, =partman-auto-raid/recipe=, and
  mdadm preseeding, but it is not selected by =preseed/debian= based on
  structured =storage.mode= and currently includes LVM-oriented behavior that
  should not be carried into plain RAID mode.
- The existing wipe early command always renders, even when =storage.wipe= is
  false, and only wipes the beginning of matched devices.

** Design Direction

- Split Debian storage rendering into named templates so the top-level preseed
  remains readable.
- Dispatch the storage recipe by =storage_mode=.
- Add a small template failure helper or equivalent render validation so query
  overrides such as =/configs/preseed/debian?storage_mode=zfs= fail clearly.
- Keep global structured storage flexible for other installers. Debian should
  reject unsupported modes when rendering =preseed/debian=, but global mapping
  validation should not preclude future OS-specific values that another
  template may support.
- Treat =plain= as a compatibility question during implementation:
  either alias it to =regular= with documentation, or reject it for Debian with
  a clear migration note.
- Decision for Phase 1: keep =plain= parseable in global mappings for
  compatibility, but reject it when rendering =preseed/debian=. Debian preseed
  supports only =regular= and =lvm= until later phases add =raid=.
- Keep =/boot= as a separate ext4 partition in both =regular= and =lvm= modes.
  This keeps bootloader behavior consistent across the two recipes and avoids
  coupling the first =regular= implementation to assumptions about firmware,
  filesystem, or future encryption support.
- Add Debian =raid= mode as RAID1-over-two-disks first. For UEFI systems, do
  not put the EFI System Partition itself on mdraid; firmware reads normal FAT
  partitions, so the RAID recipe should create an ESP on each member disk,
  mount one at =/boot/efi=, and ensure bootloader files are present on both
  disks. Use mdadm RAID1 for =/boot= and for the device that backs the root and
  swap layout.
- Keep =raid= distinct from =lvm=. Plain RAID mode should not render an LVM PV,
  VG, LV, =partman-auto-lvm/new_vg_name=, =lvm2-udeb=, or =partman-lvm=.
- Make =regular= the built-in default storage mode. This is an intentional
  behavior change: users who want the current LVM behavior should set
  =storage.mode: lvm= explicitly in mappings or pass =storage_mode=lvm=.

** RAID Boot Rationale

The RAID mode is for servers with two OS disks, such as two M.2 devices, where
the desired behavior is that the installed OS keeps running when one disk
fails.

Use plain Linux =mdadm= RAID1 for this plan because it is the lowest-risk
Debian preseed implementation for mirrored OS disks. Alternatives are valid in
other environments, but are not the target of this plan:

- Hardware RAID1 is acceptable when real hardware RAID exists, but it adds
  controller dependency and is not portable across the bare disks.
- ZFS mirrors provide stronger filesystem integrity, but Debian preseed
  root-on-ZFS boot setup is a larger project and still requires duplicated EFI
  System Partitions.
- Btrfs RAID1 and cloned independent installs introduce more boot and recovery
  policy than this plan needs.
- Stateless/PXE rebuilds help recover failed hosts, but do not keep the current
  OS running through an OS disk failure.

The important boot constraint is that UEFI firmware does not boot from mdraid
or ZFS directly. It loads EFI programs from a normal FAT EFI System Partition.
Therefore RAID mode must create a normal ESP on each disk, keep bootloader files
available on both ESPs, and use mdadm only for Linux-managed filesystems such
as =/boot=, =/=, and swap.

This remains compatible with iPXE network boot. The machine should network boot
a UEFI iPXE binary for installer startup; the UEFI-only constraint in this plan
applies to the installed OS disk boot path and ESP layout.

With one failed disk, the expected impact should be:

- The running system continues from the surviving RAID1 members.
- A reboot succeeds if the surviving disk has a valid ESP and bootloader copy.
- Recovery means replacing the failed disk, recreating its partition layout,
  copying/restoring its ESP contents, adding new members back to the md arrays,
  and allowing resync to complete.

** RAID Implementation Recommendations

- Require =boot.firmware: uefi= for Debian =storage.mode: raid=.
- Prefer stable device paths under =/dev/disk/by-id/...= for
  =storage.raid.devices=. Allow =/dev/nvme0n1= style paths for lab use and
  tests, but do not recommend them for production examples.
- Start with fixed, conservative RAID sizing:
  - 512 MiB ESP on each disk
  - 1 GiB RAID1 ext4 =/boot=
  - RAID1 swap when swap is configured
  - RAID1 ext4 root mounted at =/= with grow behavior
- Install GRUB EFI files to both ESPs and place a fallback bootloader at
  =EFI/BOOT/BOOTX64.EFI= on both disks.
- Ensure the installed system can assemble arrays during early boot by writing
  mdadm config into =/target/etc/mdadm/mdadm.conf= and running
  =in-target update-initramfs -u=.
- Add a short operator recovery runbook for failed-disk replacement after the
  first implementation lands.
- Treat render tests as necessary but insufficient. RAID mode needs at least
  manual VM install validation, including degraded reboot checks from each
  surviving disk.

** Acceptance Criteria

- Debian =storage.mode= =regular= renders a non-LVM GPT/UEFI layout.
- Debian =storage.mode= =lvm= preserves the current LVM layout behavior.
- Debian =storage.mode= =raid= renders a two-disk RAID1 GPT/UEFI layout for
  mirrored M.2 install disks.
- Debian RAID mode is UEFI-only and fails clearly for BIOS firmware.
- RAID member disks are configured as layout data, not inferred from destructive
  wipe patterns.
- Debian RAID installs are compatible with UEFI iPXE installer startup.
- Debian RAID installs configure both ESPs so the system can reboot from either
  surviving disk after one disk fails.
- Debian RAID installs write mdadm config and refresh initramfs so arrays
  assemble during installed-system boot.
- RAID mode has documented manual VM install and degraded reboot validation.
- Built-in default Debian rendering uses =regular= storage unless explicitly
  configured otherwise.
- Unsupported Debian storage modes fail clearly.
- Disk wiping is opt-in via =storage.wipe= and skips partition devices.
- Existing template names and config URLs continue to work.
- Non-Debian installer templates continue to render as they did before this
  plan.
- Render-validation tests cover regular mode, LVM mode, RAID mode, wipe true,
  wipe false, and partition-skip wipe logic.
