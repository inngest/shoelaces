* LUKS Install Profiles

** Goal

Add first-class install profiles for encrypted and unencrypted operating system
installs using the structured provisioning model from Plans 002 and 003.
LUKS should be represented as data in =mappings.yaml=, not as ad hoc flat
template params, while still leaving =installer.extraTemplate= available for
site-specific native installer behavior.

** Boundaries

- Depends on Plan 002 for named targets, koanf parsing, environment-backed
  values, and structured runtime mappings.
- Depends on Plan 003 for embedded generic provisioning defaults, structured
  users, structured provisioning fields, and =installer.extraTemplate=.
- Builds on Plan 005 for persisted boot sessions and opaque =ref= transport
  between boot scripts and =/configs/*= rendering.
- Builds on Plan 007 for Debian =storage.mode= rendering across =regular=,
  =lvm=, and =raid=.
- Scope this plan to Debian only. Within Debian, encrypted installs must support
  every Debian storage mode Shoelaces supports in this plan: =regular=, =lvm=,
  and =raid=.
- Does not reintroduce per-feature partial hooks. Common LUKS behavior should
  be modeled as structured fields; arbitrary installer snippets remain the job
  of =installer.extraTemplate=.
- Does not change UI embedding behavior.
- Does not require ansible changes in this repo, but examples should make it
  clear how an operator can pass LUKS secrets through systemd environment
  variables.

** Current State

- Current preseed files do not configure full-disk LUKS.
- =encrypt_home= only maps to =user-setup/encrypt-home= and is not LUKS.
- Structured mappings now support multiple targets and structured sections for
  =users=, =storage=, =boot=, =repos=, =installer=, and other provisioning data.
- =storage.mode= currently validates =regular=, =plain=, =lvm=, =raid=, and
  =manual= globally. Debian preseed rendering supports =regular=, =lvm=, and
  =raid=; =plain= is still parseable for older generic config but rejected by
  Debian rendering.
- Debian =regular= is the built-in default. LVM installs must opt in with
  =storage.mode: lvm=.
- Debian 13 =trixie= is the current Debian stable release and should be the
  default Debian example/recommended target. Debian 12 =bookworm= should remain
  available as an explicit oldstable target.
- Debian =raid= is implemented as a UEFI-only two-disk RAID1 layout with member
  disks configured under =storage.raid.devices=.
- Structured users already support raw values and ={ env: ENV_VAR }= values for
  password hashes and SSH keys.
- Boot scripts carry opaque boot refs and =/configs/*= resolves structured
  installer config server-side. Secret-bearing LUKS fields should use that
  server-side reference path and must not be projected into boot script URLs.
- Persisted boot session refs already provide the transport mechanism for
  server-side installer config rendering. LUKS work should extend and test that
  path rather than introduce a parallel token/cache mechanism.
- Generic redaction already treats keys containing fragments such as
  =passphrase=, =password=, =secret=, and =token= as sensitive. LUKS work still
  needs explicit tests for the chosen nested =storage.encryption= schema.
- Embedded provisioning templates currently render generic Debian, Ubuntu,
  CentOS, and CoreOS installer paths without LUKS.

** Phased Implementation Plan

*** Phase 1: Storage Encryption Schema

- [ ] Extend =StorageConfig= with a structured encryption block, for example:

  #+begin_src yaml
  storage:
    mode: lvm
    disk: /dev/sda
    volumeGroup: vg0
    encryption:
      enabled: true
      passphrase:
        env: SHOELACES_LUKS_PASSPHRASE
      cipher: aes-xts-plain64
      keySize: 512
      hash: sha512
  #+end_src

- [ ] Keep =storage.mode= focused on layout family and use
  =storage.encryption.enabled= to select encrypted variants. Avoid adding a
  separate =luks= mode unless templates prove the combined state is ambiguous.
- [ ] Support raw and environment-backed passphrases through the same resolver
  style as structured users, while treating raw values as lab-only.
- [ ] Validate encryption fields: passphrase is required when enabled, cipher
  and hash must be non-empty when provided, and key size must be positive.
- [ ] Add parser tests for valid/invalid encryption YAML.
- [ ] Add resolver tests for raw and ={ env: ENV_VAR }= passphrases.
- [ ] Add merge-order tests proving defaults, targets, and matched mappings can
  override encryption settings.

*** Phase 2: Secret Transport And Redaction

- [ ] Reuse persisted boot-session refs so installer config rendering receives
  secret-bearing provisioning values without placing raw LUKS passphrases in the
  rendered iPXE boot script or long query strings.
- [ ] Keep only the opaque =ref= in boot/config URLs and resolve secret values
  server-side during =/configs/*= rendering.
- [ ] Document the existing boot-session ref lifetime, expiration behavior, and
  failure behavior for encrypted installs.
- [ ] Redact encryption passphrases anywhere provisioning structures are logged,
  stored in events, or exposed through debug/template render logs.
- [ ] Add unit tests proving boot scripts carry only opaque references and do
  not contain raw LUKS passphrases.
- [ ] Add log/event redaction tests for raw and environment-resolved
  passphrases.
- [ ] Add integration tests covering =/poll/*= and =/configs/preseed/*= so the
  boot script can select an encrypted install without exposing the secret in
  the boot script body.

*** Phase 3: Debian LUKS Rendering

- [ ] Update the embedded Debian preseed template to render encrypted storage
  when =storage.encryption.enabled= is true.
- [ ] Keep the existing unencrypted =regular=, =lvm=, and =raid= rendering
  paths available.
- [ ] Support encrypted Debian =regular=, =lvm=, and =raid= storage modes.
- [ ] Define and document the encrypted device stack for each Debian storage
  mode, including where LUKS sits relative to partitions, LVM, mdraid, =/boot=,
  swap, root, and duplicated ESPs.
- [ ] Generate Debian preseed crypto directives from structured storage fields
  instead of flat =luks_*= params.
- [ ] Preserve =installer.extraTemplate= after structured sections so advanced
  sites can still add native Debian commands.
- [ ] Add rendering tests for supported Debian encrypted layouts plus
  regression coverage proving unencrypted =regular=, =lvm=, and =raid= still
  render.
- [ ] Add validation/rendering tests for every encrypted Debian storage mode so
  misconfigured encrypted targets fail clearly.
- [ ] Run the Debian render validation target so the encrypted and unencrypted
  preseed outputs remain syntactically valid.

*** Phase 4: Non-Debian Installer Guardrails

- [ ] Explicitly reject structured LUKS for Ubuntu minimal, CentOS kickstart,
  CoreOS, and other non-Debian installer templates in this plan.
- [ ] Document the Debian-only LUKS scope and recommend =installer.extraTemplate=
  or full template override as the escape hatch for non-Debian encrypted
  installs.
- [ ] Make unsupported encrypted installer combinations fail before rendering
  where Shoelaces can identify the selected installer template, instead of
  silently producing unencrypted install config.
- [ ] Add validation/rendering tests proving non-Debian encrypted targets fail
  clearly instead of rendering unencrypted install config.

*** Phase 5: Target Examples And Development Config

- [ ] Make Debian 13 =trixie= the default Debian example/recommended target.
- [ ] Add sample targets for Debian 13 unencrypted and Debian 13 LUKS.
- [ ] Keep Debian 12 =bookworm= available as an explicit oldstable target, but
  do not make it the default.
- [ ] Leave existing Ubuntu 24.04 and Ubuntu 26.04 examples unencrypted and make
  the docs clear that structured LUKS is Debian-only in this plan.
- [ ] Add an example showing a per-host or per-target LUKS passphrase loaded via
  ={ env: ENV_VAR }= from the systemd service environment.
- [ ] Add a raw-value example only if it is clearly marked as lab-only and not
  suitable for production.
- [ ] Update =dev/= config so local development can exercise both encrypted and
  unencrypted targets without real secrets.
- [ ] Add tests or render-validation fixtures that load the example mappings.

*** Phase 6: Documentation And Verification

- [ ] Document the structured =storage.encryption= schema and merge behavior.
- [ ] Document LUKS security tradeoffs, especially serving installer config over
  HTTP and exposing unattended install secrets to machines on the provisioning
  network.
- [ ] Document recommended use of per-host secrets, trusted networks, and TLS or
  network isolation where available.
- [ ] Document how =installer.extraTemplate= remains the escape hatch for
  native installer behavior that is not covered by structured storage fields.
- [ ] Run =make test=.
- [ ] Run =make integration=.
- [ ] Run the render validation target.
- [ ] Run =make lint=.
- [ ] Run =./scripts/check-plan-status.sh=.

** Acceptance Criteria

- [ ] LUKS and non-LUKS install targets can coexist.
- [ ] LUKS configuration is represented under structured =storage= fields.
- [ ] Debian LUKS rendering supports =regular=, =lvm=, and =raid= storage modes.
- [ ] Non-Debian encrypted targets fail clearly instead of rendering
  unencrypted installer config.
- [ ] LUKS secrets can come from explicit environment-backed values.
- [ ] Raw LUKS secret values are supported only as documented lab-only inputs.
- [ ] Existing non-LUKS =regular=, =lvm=, and =raid= Debian installs continue
  to render.
- [ ] Sensitive LUKS values are redacted from logs/events and do not appear in
  rendered boot-script URLs.
- [ ] Debian encrypted and unencrypted render-validation fixtures pass.
- [ ] =make test=, =make integration=, render validation, =make lint=, and the
  plan status checker pass.

** Notes And Risks

- Full-disk encryption through preseed exposes sensitive material to the
  installer. This should be restricted to trusted networks or HTTPS.
- Prefer per-host LUKS passphrases over shared global passphrases.
- LUKS support should not bypass the structured mappings model. Add fields to
  =StorageConfig= and renderer projections instead of adding new flat
  =params= conventions.
- Boot-session refs avoid putting raw secret material in boot-script URLs, but
  the underlying persisted boot-session payload can contain resolved
  provisioning data. Treat any LUKS passphrase storage as sensitive operational
  state and document retention, access, and cleanup expectations.
- Debian RAID support has render tests but still needs manual install and
  degraded reboot validation from Plan 007 before encrypted RAID should be
  considered for production use.
