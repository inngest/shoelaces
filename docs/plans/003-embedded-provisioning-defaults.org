* Embedded Provisioning Defaults

** Goal

Embed generic provisioning templates and static provisioning files so Shoelaces
can serve useful iPXE, preseed, kickstart, and cloud-init defaults out of the
box, while still allowing site-specific files in =data-dir= to override those
defaults.

The embedded defaults should get an OS install to a generic, non-site-specific
finish state. Site orchestration such as firstboot scripts, Ansible checkout,
SSH bootstrap keys, host enrollment, or post-install service enablement should
come from disk overrides or external automation, not from embedded production
defaults.

** Boundaries

- Do not embed =mappings.yaml= as production runtime policy.
- Do not embed credentials or site secrets.
- Do not embed Inngest/site-specific firstboot scripts, SSH keys, Ansible repo
  URLs, playbook names, or service enablement as generic runtime defaults.
- Keep UI assets under Plan 001.
- Keep the richer target/mapping schema under Plan 002.
- Preserve the Plan 001 route separation: =/static/*= remains UI-only, and
  provisioning static files are served from =/configs/static/*=.
- Preserve the Plan 002 direct-render behavior: =/configs/<template>= uses URL
  query params; mapping params are only applied during polling/manual boot
  target resolution.
- Keep =mappings.yaml= external and required site policy unless a later plan
  explicitly defines example-only embedded mappings that are not used at
  runtime.

** Current Repo Audit Notes

- Existing =configs/data-dir/static/firstboot.sh=,
  =configs/data-dir/static/firstboot.service=, SSH key references, and Ansible
  bootstrap behavior are site-shaped examples and should not become embedded
  generic defaults.
- Existing Debian preseed late_command currently installs firstboot assets. The
  embedded default should replace that with a documented no-op hook.
- A site can restore firstboot behavior by overriding the late_command partial
  and serving its scripts from disk-backed =/configs/static/*=.
- Existing template references to provisioning static files should use
  =/configs/static/*=, not UI =/static/*=.

** Desired Overlay Model

- Dynamic template parsing loads embedded provisioning templates first, then
  overlays disk templates from =data-dir=, then overlays disk environment
  overrides from =data-dir/env_overrides/<env>=.
- =/configs/*= renders embedded templates when no disk template exists, and disk
  templates take precedence when present.
- =/configs/static/*= serves provisioning static files from disk first, then
  embedded generic static defaults.
- =data-dir= remains the site override root.
- Environment overrides remain supported for disk-backed site files.
- Generic embedded templates expose a small documented set of partial hooks so
  sites can override common extension points without replacing whole OS install
  templates.
- Site-specific firstboot and post-install orchestration are implemented as
  disk overrides, not embedded defaults.
- Missing site mappings should remain a clear startup/configuration error.

** Partial Hook Model

Embedded templates should support both full template replacement and targeted
partial replacement. A disk template that defines the same template name as an
embedded template replaces that definition during parse/overlay.

Initial documented partial hooks:

- =preseed/common/locale=
- =preseed/common/network=
- =preseed/common/time=
- =preseed/common/users=
- =preseed/debian/storage=
- =preseed/debian/packages=
- =preseed/debian/late_command=
- =preseed/debian/finish=
- =ipxe/linux_args=
- =ipxe/debian/kernel_args=
- =ipxe/debian/preseed_url=
- =kickstart/centos/storage=
- =kickstart/centos/packages=
- =kickstart/centos/post=
- =cloudconfig/coreos/users=
- =cloudconfig/coreos/units=
- =cloudconfig/coreos/write_files=

** Phased Implementation Plan

*** Phase 1: Provisioning Default Audit And Sanitization

- [ ] Classify current =configs/data-dir= files as generic embeddable defaults,
  site-only examples, or tests-only fixtures.
- [ ] Remove or isolate site-specific behavior from candidates for embedded
  defaults, including firstboot scripts, Ansible checkout defaults, SSH key
  fetches, and hard-coded credentials.
- [ ] Rewrite default Debian late_command behavior to a documented no-op partial
  hook.
- [ ] Update provisioning static URL examples to use =/configs/static/*= instead
  of UI =/static/*=.
- [ ] Add tests or static checks proving embedded-default candidates do not
  include known site-only file names or secret-like placeholders.

*** Phase 2: Embedded Provisioning Filesystem

- [ ] Add an embedded provisioning filesystem helper for generic
  provisioning default contents.
- [ ] Exclude =mappings.yaml= from production runtime defaults.
- [ ] Exclude site-specific =static/firstboot.sh=,
  =static/firstboot.service=, =static/authorized_keys=, =static/id_ansible=, and
  similar bootstrap artifacts from embedded runtime defaults.
- [ ] Add tests proving representative embedded provisioning files exist.
- [ ] Add tests proving excluded site-only files are not available from the
  embedded runtime defaults.

*** Phase 3: Dynamic Template Overlay

- [ ] Update dynamic template parsing to load embedded provisioning templates.
- [ ] Overlay disk templates from =data-dir= on top of embedded defaults.
- [ ] Preserve environment override behavior for disk files.
- [ ] Preserve direct =/configs/<template>= query-param rendering behavior.
- [ ] Refactor embedded provisioning templates around documented partial hooks:
  preseed users, packages, storage, late command, finish; iPXE kernel args and
  preseed URL; kickstart packages, storage, post; cloud-init users, units, and
  write files.
- [ ] Add default no-op post-install hooks where generic installs should not run
  site-specific firstboot logic.
- [ ] Add tests for embedded fallback, full-template disk override precedence,
  and partial disk override precedence.
- [ ] Add tests proving mapping-resolved boot renders can use embedded templates
  when the selected target references an embedded template name.

*** Phase 4: Static Provisioning Overlay

- [ ] Update =/configs/static/*= serving to use disk =data-dir/static= first and
  embedded static provisioning files second.
- [ ] Preserve directory index behavior where existing tests rely on it.
- [ ] Add tests for embedded fallback, disk override, and missing file behavior.
- [ ] Add tests proving =/static/*= remains UI-only and does not serve embedded
  provisioning defaults.

*** Phase 5: Startup Without Disk Templates

- [ ] Allow Shoelaces to start with external mappings/config but without any
  disk provisioning template tree when selected targets reference embedded

- [ ] Keep clear errors when required site configuration, such as mappings, is

- [ ] Add a smoke/integration test for running with no disk provisioning

- [ ] Add an integration test proving a target from external =mappings.yaml= can

** Acceptance Criteria

- [ ] Generic provisioning templates can be served from embedded defaults.
- [ ] Generic static provisioning files can be served from embedded defaults.
- [ ] Disk =data-dir= files override embedded provisioning defaults.
- [ ] Disk templates can override documented partial hooks without replacing a
  full OS install template.
- [ ] Generic embedded templates do not trigger site-specific firstboot logic by
  default.
- [ ] =mappings.yaml= remains external runtime/site configuration.
- [ ] =/static/*= remains UI-only and =/configs/static/*= remains provisioning
  static only.
- [ ] Existing direct =/configs/<template>= query-param behavior remains
  unchanged.
- [ ] =go test ./...= passes.
- [ ] =go test -tags=integration ./test/integ-test= passes.

** Notes And Risks

- Embedded provisioning defaults should be generic and non-secret.
- The current repo examples include site-shaped defaults; review them before
  making them embedded runtime defaults.
- Disk overlay semantics should be explicit and deterministic.
- Keep the partial hook surface intentionally small. Every documented hook is a
  compatibility promise for future embedded template changes.
- Be careful not to accidentally make embedded examples into production runtime
  policy. Operators should still own mappings and site-specific install
  behavior.
