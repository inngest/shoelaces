* Embedded Provisioning Defaults

** Goal

Embed generic provisioning templates and static provisioning files so Shoelaces
can serve useful iPXE, preseed, kickstart, and cloud-init defaults out of the
box, while still allowing site-specific files in =data-dir= to override those
defaults.

The embedded defaults should get an OS install to a generic, non-site-specific
finish state. Site orchestration such as firstboot scripts, Ansible checkout,
SSH bootstrap keys, host enrollment, or post-install service enablement should
come from disk overrides or external automation, not from embedded production
defaults.

** Boundaries

- Do not embed =mappings.yaml= as production runtime policy.
- Do not embed credentials or site secrets.
- Do not embed Inngest/site-specific firstboot scripts, SSH keys, Ansible repo
  URLs, playbook names, or service enablement as generic runtime defaults.
- Keep UI assets under Plan 001.
- Keep the richer target/mapping schema under Plan 002.
- Preserve the Plan 001 route separation: =/static/*= remains UI-only, and
  provisioning static files are served from =/configs/static/*=.
- Preserve the Plan 002 direct-render behavior: =/configs/<template>= uses URL
  query params; mapping params are only applied during polling/manual boot
  target resolution.
- Keep =mappings.yaml= external and required site policy unless a later plan
  explicitly defines example-only embedded mappings that are not used at
  runtime.

** Current Repo Audit Notes

- Phase 1 classified current =configs/data-dir= files in
  =docs/provisioning-defaults-audit.md=.
- =configs/data-dir/static/firstboot.sh=,
  =configs/data-dir/static/firstboot.service=, SSH key references, and Ansible
  bootstrap behavior are site-shaped examples and must not become embedded
  generic defaults.
- The generic installer extra snippet is planned as an embedded no-op by
  default.
- A site can restore firstboot behavior by selecting an
  =installer.extraTemplate= snippet and serving its scripts from disk-backed
  =/configs/static/*=.
- Template references to provisioning static files should use =/configs/static/*=,
  not UI =/static/*=.

** Desired Overlay Model

- Dynamic template parsing loads embedded provisioning templates first, then
  overlays disk templates from =data-dir=, then overlays disk environment
  overrides from =data-dir/env_overrides/<env>=.
- =/configs/*= renders embedded templates when no disk template exists, and disk
  templates take precedence when present.
- =/configs/static/*= serves provisioning static files from disk first, then
  embedded generic static defaults.
- =data-dir= remains the site override root.
- Environment overrides remain supported for disk-backed site files.
- Generic embedded templates expose a single native installer extra-snippet
  escape hatch plus full-template replacement for behavior outside structured
  config.
- Common user/account provisioning should be data-driven from mappings through a
  structured keyed =users= model instead of requiring operators to override user
  partial templates.
- Declarative provisioning behavior such as packages, locale, time, network,
  storage, boot arguments, and repository/mirror settings should also be
  represented as structured mapping policy instead of requiring partial
  overrides for common cases.
- Site-specific firstboot and post-install orchestration are implemented as
  disk overrides, not embedded defaults.
- Missing site mappings should remain a clear startup/configuration error.

** Structured Provisioning Model

Mappings should become the source of truth for common declarative provisioning
settings. The same sections may appear in =defaults=, =targets.<name>=, and
each mapping rule. Runtime resolution merges them in the same order as params:
defaults, target, matched mapping, then generated/runtime values when a later
phase explicitly supports them.

Initial structured sections:

#+begin_src yaml
defaults:
  locale:
    language: en_US.UTF-8
    keyboard: us

  time:
    timezone: UTC
    utc: true
    ntp: true

  network:
    bootproto: dhcp
    nameservers:
      - 1.1.1.1
      - 8.8.8.8

  packages:
    install:
      - openssh-server
      - curl
      - ca-certificates
      - git
      - sudo
    groups:
      - core
    updatePolicy: unattended-upgrades

  storage:
    disk: /dev/nvme0n1
    wipe: true
    mode: lvm
    volumeGroup: vg0
    filesystems:
      root:
        mountpoint: /
        fstype: ext4
        size: grow
      swap:
        fstype: swap
        sizeMiB: 8192

  boot:
    firmware: uefi
    netboot:
      method: ipxe
      kernelArgs:
        - console=ttyS0
        - loglevel=6
    installed:
      bootloader: grub
      timeoutSeconds: 5
      kernelArgs:
        - consoleblank=0
        - sysrq_always_enabled

  repos:
    osMirror: http://deb.debian.org/debian
    firmware: true
    contrib: true
    nonFree: true

targets:
  debian12:
    script: debian.ipxe
    installer:
      configTemplate: preseed/debian
      extraTemplate: provisioning/extra
      configParams:
        encrypt_home: false
    packages:
      install:
        - qemu-guest-agent
    repos:
      release: bookworm

macMaps:
  - mac: "0c:42:a1:c3:52:96"
    defaultTarget: debian12
    targets:
      - debian12
    network:
      hostname: iad-1
    storage:
      disk: /dev/nvme1n1
#+end_src

The boot fields intentionally separate netboot from installed-system boot:

- =boot.firmware= describes the machine/install firmware target, such as =uefi=
  or =bios=.
- =boot.netboot.method= describes how Shoelaces serves the network boot path,
  currently =ipxe=.
- =boot.netboot.kernelArgs= replaces generic iPXE/Linux argument partials such
  as =ipxe/linux_args=.
- =boot.installed= describes the installed OS bootloader, such as GRUB timeout
  and installed kernel arguments.

The =installer= section describes the installer configuration served after the
netboot stage:

- =installer.configTemplate= selects the dynamic config template, such as
  =preseed/debian=, =preseed/ubuntu-minimal=, =centos.ks=, or
  =cloudconfig-coreos=.
- =installer.configParams= contains explicit query/config parameters needed by
  that installer config while templates are migrated to structured data.
- =installer.extraTemplate= selects a native installer snippet template rendered
  near the end of the installer config. The embedded default is
  =provisioning/extra=, which is a no-op.
- Together with =repos= and =boot.netboot=, =installer= replaces iPXE URL
  partials such as =ipxe/debian/preseed_url= and distro-specific kernel argument
  partials.

Structured config should replace declarative partial overrides as a breaking
change. It should not try to model arbitrary post-install automation. Keep
=installer.extraTemplate= as the unstructured escape hatch for imperative or
site-specific behavior.

The selected extra template is intentionally installer-native. A Debian target
can include =d-i preseed/late_command= or any other preseed lines; a kickstart
target can include =%post= or other kickstart sections; a cloud-init target can
include =runcmd:=, =write_files:=, =units:=, or other valid cloud-init YAML.
Shoelaces should not parse, validate, normalize, or make correctness guarantees
for the extra snippet beyond normal Go template rendering. Operators own the
installer-specific syntax they place there.

The extra snippet can download raw static scripts from =/configs/static/*= or
templated scripts from =/configs/<template>=. Full-template overrides remain the
broader escape hatch when a site needs behavior outside the structured model.

** Structured Users Model

User and account provisioning should be represented as structured runtime
mapping policy. The common path should not require a =users.slc= partial
override.

Users are keyed by username so defaults, targets, and matched mappings can merge
deterministically. =root= is not a separate schema branch; it is the normal
=users.root= account key with OS-specific rendering behavior.

#+begin_src yaml
defaults:
  users:
    root:
      system: true
      locked: true
      passwordCrypted:
        env: SHOELACES_ROOT_PASSWORD_CRYPTED

    infra:
      primary: true
      fullName: Infrastructure User
      locked: false
      passwordCrypted:
        env: SHOELACES_INFRA_PASSWORD_CRYPTED
      sshAuthorizedKeys:
        - env: SHOELACES_INFRA_SSH_KEY
        - "ssh-ed25519 AAAA... example"
      groups:
        - sudo
      shell: /bin/bash
      sudo: "ALL=(ALL) NOPASSWD:ALL"

targets:
  debian12:
    script: debian.ipxe
    users:
      infra:
        fullName: Debian Infrastructure User

macMaps:
  - mac: "0c:42:a1:c3:52:96"
    defaultTarget: debian12
    targets:
      - debian12
    users:
      infra:
        sshAuthorizedKeys:
          - env: SHOELACES_HOST_INFRA_SSH_KEY
      breakglass:
        locked: true
#+end_src

Initial fields:

- =primary=: marks the account used for installer-specific single-user fields,
  such as Debian preseed's regular install user.
- =system=: marks system accounts. =root= should normally set this implicitly.
- =locked=: disables password login when true.
- =absent=: removes or suppresses an inherited user from the resolved account
  set.
- =fullName=: human-readable display name.
- =passwordCrypted=: crypted password hash as either a raw value or ={ env:
  ENV_VAR }=.
- =sshAuthorizedKeys=: list of raw or environment-backed public keys.
- =groups=: supplementary groups.
- =shell=: login shell.
- =sudo=: sudoers rule text for renderers that support it.

Merge order should match parameter resolution: =defaults.users=,
=targets.<name>.users=, matched mapping =users=, then generated/runtime values
if a later phase explicitly supports them. User maps merge by username. Fields
for the same username merge by key, =absent: true= suppresses inherited users,
and exactly one non-root account should resolve as =primary= for preseed
rendering.

The structured user resolver should project common user data into the existing
template parameter names while templates are migrated:

- =install_username=
- =install_user_fullname=
- =install_user_password_crypted=

After OS templates render directly from normalized structured data, the
dedicated user, package, locale, time, network, storage, boot, and repo partial
hooks should be removed from the supported override contract. Post-install and
script snippets remain useful through =installer.extraTemplate=.

** Override Model

Embedded templates should support full template replacement and target-selected
native installer extra snippets. A disk template that defines the same top-level
template name as an embedded template replaces that definition during
parse/overlay.

Extra snippets are provided as normal Shoelaces =.slc= templates under
=data-dir=. The file path is for operator organization and template discovery.
The selected =installer.extraTemplate= value is the template ={{define "..."}=
name to render. The default is =provisioning/extra=.

#+begin_src text
data-dir/
  provisioning/
    extra.slc
#+end_src

#+begin_src gotemplate
{{define "provisioning/extra" -}}
d-i preseed/late_command string \
  in-target /bin/sh -c 'echo site late_command override'
{{end}}
#+end_src

This content is rendered verbatim into the installer config. For a Debian
target, the snippet can include preseed lines. For a kickstart target, use a
different target-selected template containing kickstart-native syntax:

#+begin_src yaml
targets:
  centos8:
    script: centos.ipxe
    installer:
      configTemplate: centos.ks
      extraTemplate: provisioning/centos-extra
#+end_src

#+begin_src gotemplate
{{define "provisioning/centos-extra" -}}
%post
#!/bin/bash
echo site post install
%end
{{end}}
#+end_src

For larger behavior, operators should avoid inlining long shell programs into
the installer config. The extra snippet can download a script supplied by the
site instead.

For a raw static script, place the script under disk-backed
=data-dir/static=:

#+begin_src text
data-dir/
  static/
    late-command.sh
#+end_src

Then reference it through =/configs/static/*=:

#+begin_src gotemplate
{{define "provisioning/extra" -}}
d-i preseed/late_command string \
  wget -O /target/usr/local/sbin/late-command.sh http://{{ .baseURL }}/configs/static/late-command.sh; \
  chmod 0755 /target/usr/local/sbin/late-command.sh; \
  in-target /usr/local/sbin/late-command.sh
{{end}}
#+end_src

For a script that needs Shoelaces template params, place a dynamic template under
=data-dir=:

#+begin_src text
data-dir/
  scripts/
    late-command.sh.slc
#+end_src

#+begin_src gotemplate
{{define "scripts/late-command.sh" -}}
#!/bin/sh
set -eux

hostnamectl set-hostname {{ .hostname }}
{{end}}
#+end_src

Then reference it through =/configs/<template>= and pass the required query
params explicitly:

#+begin_src gotemplate
{{define "provisioning/extra" -}}
d-i preseed/late_command string \
  wget -O /target/usr/local/sbin/late-command.sh "http://{{ .baseURL }}/configs/scripts/late-command.sh?hostname={{ .hostname | urlquery }}"; \
  chmod 0755 /target/usr/local/sbin/late-command.sh; \
  in-target /usr/local/sbin/late-command.sh
{{end}}
#+end_src

Environment-specific partials use the existing environment override tree and the
same template name:

#+begin_src text
data-dir/
  env_overrides/
    production/
      provisioning/
        extra.slc
#+end_src

#+begin_src gotemplate
{{define "provisioning/extra" -}}
d-i preseed/late_command string \
  wget -O /target/usr/local/bin/firstboot.sh http://{{ .baseURL }}/configs/static/firstboot.sh; \
  chmod 0755 /target/usr/local/bin/firstboot.sh
{{end}}
#+end_src

Full-template overrides work the same way but define the top-level template name
instead, such as ={{define "preseed/debian"}}...{{end}}=. A full-template
override should be used when a site needs to replace the whole install template.

The embedded defaults should define =provisioning/extra= as an empty/no-op
template. Targets that need installer-specific snippets can set
=installer.extraTemplate= to another template name. Disk overrides for selected
extra template names are rendered verbatim, so their syntax is deliberately the
operator's responsibility.

** Notes And Risks

- Embedded provisioning defaults should be generic and non-secret.
- The current repo examples include site-shaped defaults; review them before
  making them embedded runtime defaults.
- Disk overlay semantics should be explicit and deterministic.
- Keep the partial hook surface intentionally small. Every documented hook is a
  compatibility promise for future embedded template changes.
- Be careful not to accidentally make embedded examples into production runtime
  policy. Operators should still own mappings and site-specific install
  behavior.
