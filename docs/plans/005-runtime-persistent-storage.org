* Runtime Persistent Storage

** Goal

Introduce a durable runtime storage layer for Shoelaces so operational data can
survive process restarts and host reboots, and so boot/config requests can refer
to previously resolved data by stable references instead of carrying all values
through transient memory or long query strings.

** Boundaries

- This is runtime persistence, not provisioning template storage. Embedded web
  assets and embedded provisioning defaults remain static code assets.
- =data-dir= remains the operator-owned root for runtime configuration,
  provisioning overrides, static config assets, and the new persistent runtime
  database.
- Do not store raw secrets in events, logs, UI responses, or reference records
  unless a later phase explicitly adds an encrypted-at-rest secret design.
- Preserve current behavior for operators who do not need persistence beyond the
  new default database file.
- Keep the implementation single-node first. HA, replication, and external SQL
  services are out of scope for this plan.

** Current State

- Shoelaces keeps waiting/manual boot server state in memory via
  =server.States=.
- Shoelaces keeps UI event history in memory via =event.Log=.
- A restart loses waiting hosts, manual target selections, and event history.
- Installer config rendering is mostly stateless. Structured provisioning data
  needed by =/configs/*= requests is serialized into URL query values.
- The query-based flow works for non-secret configuration, but it is a poor fit
  for larger structures and future secret-bearing data such as LUKS passphrases.

** Design Direction

- Add a small persistence package with clear repository interfaces instead of
  letting handlers or polling code write SQL directly.
- Shape those interfaces around CQRS boundaries: command interfaces own writes
  and transactional mutations, while query interfaces own read models used by
  the UI, polling, and rendering code.
- Use SQLite as the default local backend, stored under =data-dir=, because
  Shoelaces is currently a single-process service and should not require an
  external database for normal deployments.
- Use =sqlc= for database access. Keep SQL in checked-in schema and query files,
  generate typed Go accessors, and keep application code behind repository
  interfaces rather than embedding raw SQL strings throughout the codebase.
- Use =goose= for database migrations and schema version tracking across SQL
  backends. SQLite is the first backend, and future Postgres support should add
  its own Goose migrations behind the same persistence boundary.
- Keep backend-specific generated code behind those CQRS interfaces so a future
  Postgres backend can provide the same command/query contracts without
  changing handlers, polling, or template rendering.
- Keep an in-memory backend for fast unit tests and for any explicit
  no-persistence development mode.
- Use persistent boot/config references for data that must be reused later by
  installer config requests. The boot script should carry an opaque reference,
  and Shoelaces should resolve the reference server-side.
- Keep retention explicit so operational history does not grow forever.

** Proposed Configuration

#+begin_src yaml
data-dir: /etc/shoelaces/data-dir

persistence:
  backend: sqlite
  path: runtime/shoelaces.db
  retention:
    events: 720h
    bootSessions: 24h
#+end_src

- =persistence.backend= starts with =sqlite= and =memory=.
- =postgres= is a future backend option. The public persistence boundary should
  be designed so adding it mostly means new sqlc config, schema/query files,
  connection setup, and backend wiring.
- =persistence.path= is relative to =data-dir= unless absolute.
- =persistence.retention.events= controls UI/audit event retention.
- =persistence.retention.bootSessions= controls reference/session retention.

** Acceptance Criteria

- [ ] Shoelaces starts with default SQLite persistence under =data-dir=.
- [ ] Events survive Shoelaces process restarts and host reboots when the same
  =data-dir= is reused.
- [ ] Waiting/manual boot state can survive a restart until its retention window
  expires.
- [ ] Boot/config rendering can use opaque references to retrieve previously
  resolved data.
- [ ] Existing UI routes and JSON response shapes remain compatible unless a
  documented versioned change is introduced.
- [ ] Existing direct query-param rendering still works where it is currently
  supported.
- [ ] Secret-bearing or sensitive values are redacted in persisted events and
  UI/API responses.
- [ ] Retention cleanup bounds persistent database growth.
- [ ] =make gen= regenerates checked-in sqlc files for the persistence backend.
- [ ] CI fails when sqlc generated files are stale.
- [ ] =make test=, =make integration=, render validation, =make lint=, and the
  plan status checker pass.

** Notes And Risks

- SQLite is a good fit for single-node Shoelaces, but it should not be presented
  as a clustered persistence story.
- =sqlc= keeps SQL explicit and reviewable without scattering raw SQL strings
  across handlers or services. Repository interfaces should remain the boundary
  consumed by the rest of Shoelaces.
- CQRS should be a boundary, not ceremony. Avoid duplicating business logic
  between command and query implementations; use it to keep writes, read models,
  and backend-specific generated code decoupled.
- A future Postgres backend may need different SQL and migrations. The command
  and query contracts should be tested as backend behavior, not as SQLite
  implementation details.
- Persisting resolved boot data changes the failure mode of =/configs/*=
  requests: a missing or expired reference should fail clearly and safely.
- This plan should make future LUKS support safer by avoiding secret-bearing
  query strings, but encrypted-at-rest secret management is still a separate
  design decision.
- Database retention must be conservative enough for unattended installs that
  take a long time, especially when hosts reboot between installer stages.
- The term "storage" is already used for disk layout in mappings. Code and docs
  should prefer "persistence" or "runtime persistence" to avoid confusion.
